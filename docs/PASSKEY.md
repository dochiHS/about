## ① 무엇으로 붙였나

| 구분 | 이름 | 쓰인 곳 |
|---|---|---|
| **라이브러리** (서버) | SimpleWebAuthn `@simplewebauthn/server` 13.3.3 | 질문 만들기, 등록 응답·로그인 서명 확인 |
| **라이브러리** (브라우저) | SimpleWebAuthn `@simplewebauthn/browser` 13.3.0 | `navigator.credentials.create/get` 호출을 감싸는 얇은 도구. 파일을 저장소에 그대로 포함 |
| 서버 실행 | Supabase Edge Function `passkey` (Deno) | `supabase/functions/passkey/index.ts` |

인증 서비스(Supabase Auth 등)는 쓰지 않았습니다. 세션 발급·확인·로그아웃은 직접 구현했고, WebAuthn 검증만 라이브러리에 맡겼습니다.

## ② 왜 그걸 골랐나

- **라이브러리 vs 직접 구현**: 서명 확인에는 CBOR 해석, COSE 공개키 변환, DER 서명, rpIdHash·flags·counter 확인이 모두 들어갑니다. 한 군데만 틀려도 "서명이 늘 통과"하는 구멍이 생기므로, 널리 쓰이는 검증 라이브러리에 맡기고 나는 **질문 보관·일회성·세션·권한** 쪽에 집중했습니다.
- **인증 서비스가 아닌 이유**: 과제의 핵심(서버가 질문을 보관하고, 한 번 쓰면 버리고, 공개키로 확인한다)이 서비스 안에 숨으면 "어디를 지나는지"를 소스로 보여 줄 수 없습니다.
- **Supabase Edge Function**: T01 페이지는 GitHub Pages(정적)라 서버가 없습니다. T06·T07에서 이미 쓰던 무료 프로젝트에 함수 하나만 더하면 되고, 이 프로젝트에는 일시정지 방지(keepalive)가 이미 돌고 있어 나중에 채점할 때도 서버가 깨어 있습니다.
- **SimpleWebAuthn 13.x (14.x 아님)**: 14.0.0이 이 과제 한 달 전(2026-09-02)에 나와 Deno 런타임에서 오래 검증된 13.x 마지막 판을 골랐습니다.

## ③ 어디를 어떻게 고쳤나 — 네 흐름이 지나는 자리

T01의 01~05 공개 소개는 **한 줄도 지우거나 바꾸지 않았습니다**(`index.html`은 추가만: `vault.css` 연결 1줄, 경계선+06 섹션, 스크립트 3줄). 06 섹션의 HTML에는 빈 틀만 있고 비공개 내용은 없습니다.

| 흐름 | 화면 (`vault/vault.js`) | 서버 (`supabase/functions/passkey/index.ts`) |
|---|---|---|
| **등록** | `register()` 91행 → `/register/options` → `SimpleWebAuthnBrowser.startRegistration` → `/register/verify`. 취소하면 105행에서 `/register/cancel` | `POST /register/options` 276행: 질문 생성 후 `pk_challenges`에 보관(5분). `POST /register/verify` 321행: 질문을 `consumeChallenge`(93행)로 **한 번만** 꺼내고, 335행 `verifyRegistrationResponse`로 확인 → 공개키만 `pk_credentials`에 저장. `POST /register/cancel` 315행: 안 쓴 질문 삭제 |
| **로그인** | `login()` 127행 → `/login/options` → `startAuthentication` → `/login/verify` | `POST /login/options` 366행: 새 질문 보관. `POST /login/verify` 377행: 질문 소비 → 등록된 패스키 찾기 → userHandle이 주인과 같은지(388행) → 392행 `verifyAuthenticationResponse`로 **저장된 공개키로 서명 확인** → 세션 발급 `newSession`(233행) |
| **로그아웃** | `logout()` 152행 | `POST /logout` 407행: 세션에 `revoked_at` 기록(409행) |
| **비공개 자료 조회** | `loadVault()` 162행, 헤더 `x-session` | `requireSession` 221행(없으면·틀리면·로그아웃됐으면 401) → `GET /vault` 419행, `/notes/:id` 440행(남의 것이면 **403 `not_yours`** 445행), `/credentials/:id` 461행(남의 것 403 466행, 마지막 하나 삭제 **409 `last_passkey`** 474행, 지운 패스키로 열린 세션 끊기 478행) |

**남의 자료 거절을 만드는 소스 (C41)**: `index.ts` 221행 `requireSession`(누구인지는 세션만 정함) + 445행·466행 `if (주인 !== 세션의 사람) fail(403, "not_yours")` + 430행 `POST /notes`(본문에 `user_id`를 적어 보내도 무시하고 세션의 사람으로 저장) + 419행 `GET /vault`(주소의 `?user=`를 무시).

**로그인 뒤 사람을 알아보는 방법 (C32)**: **세션 토큰**입니다. 로그인에 성공하면 서버가 32바이트 무작위 토큰을 한 번 돌려주고, DB(`pk_sessions`)에는 그 **SHA-256 값만** 저장합니다. 브라우저는 이 탭의 `sessionStorage`에만 두고 요청 헤더 `x-session`으로 보냅니다(쿠키 아님). 8시간 뒤 만료, 로그아웃하면 즉시 무효.

**서버에 저장되는 값 (C21·C22)**: `pk_credentials.public_key` = COSE 형식 **공개키**(base64url). 풀어 보면 `{kty: EC2, alg: ES256, crv: P-256, x, y}`뿐이고 개인키 성분(`d`)은 없습니다. 이것은 비밀번호가 아닙니다. 누가 가져가도 로그인할 수 없고, 로그인하려면 기기 안의 개인키로 새 질문에 서명해야 합니다.

**DB 권한**: `pk_*` 표는 RLS를 켜고 anon·authenticated 권한을 모두 회수했습니다. 서버(service_role)만 읽고 씁니다. 공개용 키로 REST에 직접 요청하면 `401 permission denied`입니다(확인 기록 ①).

## ④ 안 열리는 것을 확인한 기록

전체 요청·응답: [`docs/evidence/T08_확인기록_20260928-1000.md`](evidence/T08_확인기록_20260928-1000.md). 실제 서버(`…supabase.co/functions/v1/passkey`)에 실제 요청을 보낸 기록이고, 세션 토큰은 앞 6자만 남기고 가렸습니다. 검사용 계정 두 개는 확인 기록기(`checks/evidence.html`)가 시험용 소프트웨어 패스키로 만든 것입니다.

| 확인 | 통과한 요청 | 거절된 요청 |
|---|---|---|
| **로그인 없이 열기** | A 세션으로 `GET /vault` → **200** (내 항목 3개) | 세션 없이 `GET /vault` → **401** `no_session` · 지어낸 값 → **401** `bad_session` · 공개용 키로 DB REST 직접 → **401** permission denied · 로그인 없이 받은 `index.html`·`vault.js`에서 비공개 제목·본문 검색 **0건** |
| **남의 패스키로 열기** | A 세션으로 A 항목 `GET` → **200** | A 세션으로 B 항목 읽기·고치기·지우기 → **403 / 403 / 403**. B 세션으로 A 항목 읽기·지우기·A 패스키 지우기 → **403 / 403 / 403**. 거절 앞뒤 B 항목 **3 → 3개**(내용 동일). 주소에 `?user=<B>`, 본문에 `user_id: <B>`를 적어도 **A 자료만** 돌아오고 새 항목은 A 것이 됨 |
| **이미 쓴 질문 재사용** | 새 질문 + 올바른 서명 → **200** 세션 발급 | 방금 성공한 요청 그대로 다시 → **401** `challenge_used`. 예전 서명을 새 질문 번호에 붙임 → **401** `signature_rejected`. 서명 한 바이트 변조 → **401** `signature_rejected`. 로그아웃한 토큰으로 `/vault` → **401** `session_revoked` |
| **패스키 삭제 뒤 로그인** | 두 번째 패스키로 로그인 → **200** | 지운 첫 패스키로 로그인 → **401** `unknown_credential`. 지운 패스키로 **이미 열려 있던 세션**도 → **401** `session_revoked`. 마지막 남은 패스키 삭제 → **409** `last_passkey` |

질문이 매번 다르다는 기록(C20·C28): 등록 질문 2개, 로그인 질문 3개가 모두 달랐습니다(기록 ②·③에 값 그대로). 등록 요청 본문(C23)의 칸은 `id, rawId, type, authenticatorAttachment, clientExtensionResults, response{clientDataJSON, attestationObject, transports}`뿐이고, 기기의 개인키 `d` 값을 본문 전체에서 찾은 결과는 0건이었습니다.

로컬에서도 크로미움 **가상 인증기**(실제 WebAuthn 흐름)로 화면을 직접 눌러 보는 자동 검사 46개를 통과했습니다(`checks/local/e2e.mjs`): 등록 취소 안내, 같은 기기 중복 등록 안내, 두 번째 패스키, 로그아웃 뒤 잠김, 마지막 패스키 지우기 버튼 막힘, 모바일 375px 가로 넘침 없음 등.

**패스키를 저장한 곳 (C26)**: 첫째 = **구글 비밀번호 관리자**(구글 계정에 동기화, PC·휴대폰 크롬 모두에서 보임), 둘째 = **삼성 패스**(휴대폰 기기 안). 보안 키는 쓰지 않았습니다.

서버 DB에 남은 값(`pk_credentials`, 공개키는 앞부분만): 두 줄 모두 `public_key`가 `pQECAyYgASFY…`로 시작하는 103자 COSE 공개키입니다(`a5 01 02 03 26 20 01 21 58 20 …` = kty EC2, alg ES256, crv P-256, x, y). 비밀번호 칸은 표에 아예 없습니다.

**패스키가 하나도 남지 않으면 (C46)**: 화면의 마지막 패스키 "지우기" 버튼은 막혀 있고, 서버도 `409 last_passkey`로 거절합니다. 이 자리에는 비밀번호가 없어서 0개가 되면 저를 포함해 누구도 다시 들어올 수 없기 때문입니다. 이 설명은 화면 06 아래쪽에도 적혀 있습니다.

제출 뒤 새 계정 만들기는 닫았습니다(`pk_settings.registration_open = false`). 심사하는 분은 아무것도 등록하지 않아도 되고, 잠긴 자리는 열 필요가 없습니다.

## ⑤ AI와 나

- **AI에게 맡긴 일**: 서버·화면 코드 작성, SQL, 확인 기록기와 시험용 소프트웨어 패스키, 로컬 자동 검사, GitHub 업로드와 함수 배포 조작, 이 설명서 초안.
- **내가 직접 판단한 일**: T01 소개 페이지는 그대로 두고 맨 아래에만 잠긴 자리를 붙이기, 비공개 항목 3개의 내용(모두 지어낸 것), 첫 패스키는 구글 비밀번호 관리자·두 번째는 삼성 패스에 두기, 지문·화면 잠금으로 실제 등록·로그인한 것.
- **AI 제안을 따르지 않은 일**: AI는 두 번째 패스키를 PC 화면의 "휴대전화 사용 → QR 코드"로 등록하라고 안내했지만, 저는 QR을 쓰지 않고 휴대폰 크롬에서 직접 들어가 **삼성 패스**에 저장했습니다. 저장소가 구글 비밀번호 관리자와 완전히 다른 곳(다른 회사·다른 동기화)이어야 한쪽을 잃어도 들어올 수 있다고 판단했습니다.

## ⑥ 아직 못 막은 것

1. **요청 횟수 제한이 없습니다.** 누구나 `POST /login/options`를 끝없이 불러 `pk_challenges` 표에 질문을 쌓을 수 있습니다. 질문은 5분 뒤 무효가 되지만 행은 하루가 지나야 지워지므로, 마음먹으면 무료 DB 용량을 채울 수 있습니다. 막으려면 IP별 속도 제한이 필요한데 Edge Function만으로는 믿을 만한 IP를 얻기 어려워 두었습니다.
2. **어떤 인증기인지 확인하지 않습니다(attestation `none`).** 서버는 공개키가 진짜 휴대폰·보안 키에서 왔는지 따지지 않습니다. 이 과제의 확인 기록기가 브라우저 안의 소프트웨어 패스키로 계정을 만들고 통과한 것이 바로 그 증거입니다. 개인키를 안전하게 지키는 것은 사용자의 기기에 달려 있습니다.
3. **새 계정 만들기가 열려 있는 동안은 누구나 계정을 만들 수 있습니다.** 확인 기록을 남기려고 열어 두었다가 `pk_settings.registration_open = false`로 닫았습니다. 다시 열면 그동안은 누구나 계정을 만들 수 있고, 아이디 선점도 막지 못합니다. 닫아도 이미 만든 계정에 패스키를 더하는 것은 로그인한 본인만 가능합니다.
4. **세션 토큰이 브라우저 `sessionStorage`에 있습니다.** 페이지에 XSS가 생기면 탭이 열린 동안 토큰을 훔쳐 최대 8시간 쓸 수 있습니다. 화면은 모든 값을 `textContent`/이스케이프로만 넣지만, T01부터 쓰던 외부 글꼴 CDN이 있어 CSP로 완전히 잠그지는 못했습니다.
5. **남의 항목 번호를 넣으면 403(있음)과 404(없음)가 달라서** 그 번호의 항목이 있다는 사실은 알 수 있습니다. 번호가 무작위 UUID라 추측은 사실상 어렵지만, 존재 여부를 숨기지는 않습니다.
